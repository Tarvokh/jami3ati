# سيناريو العرض التجريبي (Demo Script) — Tira Mail

> **المسودة الأولى (التركيز الحالي).** هذا السيناريو مبني على ما تحقق حيًا خلال جولة
> التسجيل البعيد، ولا يحتوي أي ميزة وهمية: كل مشهد ينفّذ خطوة بخطوة عبر HTTP حقيقي.

## المشهد 1 — بوابتا الدخول (كلمة مرور + توكن)

**الهدف:** إظهار مسارَي الدخول منظورين.

| الخطوة | الطلب | النتيجة المتوقعة |
|---|---|---|
| فتح `/login` | GET | 200 — صفحة الدخول |
| كلمة مرور | نموذج `mode=password` (`email` + `password`) | حقل `autocomplete="current-password"` |
| توكن | `details.auth__help` → نموذج `mode=token` (`token`) | مسار الاستعادة/التهيئة |

- النص الموجز: «كلمة مرور واجهة Tira فقط، وليست كلمة مرور Stalwart أو IMAP».
- ملاحظة الجلسة: كوكي `tira_token` HttpOnly + SameSite=Strict، 7 أيام.

## المشهد 2 — الدخول الحقيقي → الجلسة

**الهدف:** دخول Argon2id حقيقي → جلسة واحدة.

- POST `/login` (`mode=password`) → **303** → `/mail/<mailbox_id>` + `Set-Cookie`.
- بعد الدخول مباشر إلى الوارد (HTMX `/mail/{id}`).

## المشهد 3 — الوارد → فتح الرسالة وقراءتها

**الهدف:** اكتشاف الرسالة الحقيقية.

- GET `/mail/<mailbox_id>` → القائمة (رسائل حقيقية، e.g. رسالة «السلام عليكم»).
- GET `/mail/<mailbox_id>/message/<message_id>` → القارئ: العنوان، الجسم النصي، «إلى»،
  أزرار **نسخة للطباعة**، **تنزيل .eml**، وزر **الرد** (روابط عميقة إلى
  `/mail/<mailbox_id>/compose?to=<sender>&subject=Re%3A…`). مع بطاقة «التحقق
  البريدي» (SPF/DKIM/DMARC) في البطاقة الجانبية. بند «المرفقات» بقى في
  «غير متاح بعد» (`دعم المرفقات غير مربوط بعد`).

## المشهد 4 — الملف الشخصي والأمان

**الهدف:** كشف إدارة الهوية والجلسات.

- GET `/profile` → الملف الشخصي الحقيقي (الاسم الظاهر، تغيير كلمة المرور، الجلسات).
- POST `/profile/password` → إبطال الجلسات الأخرى.

## المشهد 5 — الإثبات الأمني

**الهدف:** إظهار حالة الحماية.

- GET `/api/v1/sovereignty-proof` → إثبات التحكم.
- رؤوس الأمنية: CSP، Referrer-Policy، nosniff، X-Frame-Options DENY، HSTS، Permissions-Policy.

## المشهد 6 — الخروج والخاتمة الصادقة

- POST `/logout` → عاد إلى `/login`.

## المشهد 7 — الرد والإرسال (مسار Black-Box متصل)

**الهدف:** إظهار دورة الرد كاملة عبر مسار الإرسال.

- GET `/mail/<mailbox_id>/compose?to=<sender>&subject=Re%3A…` → نموذج التحرير مع
  `to`/`subject` prefilled و`body` فارغ.
- POST `/mail/<mailbox_id>/send` (`to`, `subject`, `body`) →
  - **نجاح:** `303` → `/mail/<mailbox_id>?sent=<uuid>`؛ الرسالة تدخل قائمة
    الوارد الحقيقية، وتظهر لافتة `sent-notice` تقول ما جرى بالضبط: «قبِل
    المرحّل الرسالة (250)» مع المستلم والموضوع والوقت و`host:port` المرحّل،
    وتنصّ على أنه **ليس إثبات وصول** ولا توجد نسخة في مجلد «مُرسَل». اللافتة
    صادرة من الذاكرة بمعرّف عشوائي مربوط بالصندوق، تنتهي بعد 10 دقائق؛ إعادة
    تحميل الرابط بلا المعرّف أو بمعرّف مزوَّر لا تُظهر شيئًا.
  - **فشل:** إعادة شاشة التحرير مع رسالة عربية (`compose__error`).

## المشهد 8 — سجلات نطاق المرسل في القارئ (SPF / DKIM / DMARC)

**الهدف:** إظهار **سجلات DNS المنشورة** لنطاق المُرسل من نفس الأدلة التي تُبنى
منها الإثبات الأمني — بلا ادعاء مصادقة هذه الرسالة.

- GET `/mail/<mailbox_id>/message/<message_id>` → البطاقة الجانبية
  «سجلات نطاق المرسل» (`reader-auth`): وجود سجلات SPF/DKIM/DMARC/MX/MTA-STS/
  TLS-RPT للنطاق، بتسميات «موجود»/«تنبيه»/«غير مستوفٍ» وسبب الخلل عند النقص.
- سطر النطاق داخل البطاقة يقول صراحة: هذه فحوص سجلات DNS، **لا** نتيجة
  المصادقة لهذه الرسالة؛ لا يُفحص توقيع DKIM ولا نتيجة SPF/DMARC عند الاستلام.
  التسميات السابقة (`سليم`/`فشل`) كانت تُقرأ كحكم على الرسالة، فأُزيلت.
- عند غياب الأدلة المخزّنة للنطاق: «تعذّر قراءة سجلات DNS المخزّنة لهذا
  النطاق؛ لا يُعرض أي حكم بدلًا من ذلك» — لا نجاح وهمي.
- الاستجابة الحقيقية: `v=spf1 mx -all` (SPF)، DKIM RSA-2048 + Ed25519 (تحقق
  مسبق), DMARC `p=reject` (المرحلة النهائية).
- بعد توسيع DKIM (الوحدة 3): مفتاحان جديدان مُولَّدان (RSA-2048 + Ed25519) بـ
  selectors جديدة (`v1-rsa-20261112`, `v1-ed25519-20261112`) مع الحفاظ على المفاتيح
  القديمة (`v1-rsa-20261104`, `v1-ed25519-20261104`)، وبناء الإثبات عاد `pass` مع
  **4 مفاتيح نشطة** مفحوصة من الـ zone.

## خاتمة العرض

- **الإثبات:** جولة حقيقية عبر Brave (Chromium) — دخول → قراءة → جلسة.
- **المسار المعتمد:** كلمة مرور (`Argon2id`)؛ التوكن مسار تهيئة/استعادة.
- **النطاق:** استقبال Black-Box عبر Stalwart + واجهة Tira (RLS، audit trail، throttling).

- ✅ المشهد 4: **متحقق** (صفحة /profile تعرض الحالة الحقيقية).
- ✅ المشهد 5: **متحقق** (API + رؤوس الأمنية).
- ✅ المشهد 6: **متحقق** (تسجيل الخروج).
- ✅ المشهد 7 (جديد): **متحقق** (الرد → compose → send عبر relay محلي → 303 → الوارد).
- ✅ المشهد 8 (جديد): **متحقق** (بطاقة تحقق البريد: SPF/DKIM/DMARC من الأدلة الفعلية → pass).

**المرحلة E مكتملة** (11 نوفمبر 2026): SPF/DKIM/DMARC في واجهة القارئ عبر
`proof::mail_authentication_for` + `MessageAuth` في الواجهة؛ الأبواب خضراء
(242 اختباراً) وبناء ناجح، والتحقق الحي أكد البطاقة بفحوص حقيقية.

**الوحدة 3 مكتملة** (12 نوفمبر 2026): توسيع DKIM — مفاتيح RSA-2048 + Ed25519 جديدة
بـ selectors جديدة (`v1-rsa-20261112`, `v1-ed25519-20261112`) مع تحديث zone والـ
artifact، وكل الفحوص DKIM عادت `pass` (4 مفاتيح نشطة)، وإثبات التحقق الحي
`status = "pass"`.

الخطوة التالية: التقرير النهائي + اللقطة الأخيرة + freeze.
