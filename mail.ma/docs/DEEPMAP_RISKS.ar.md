# عمق المعمارية ومخاطر Tira Mail — تقرير التحليل المتعمق

توثيق مباشر لنتائج فحص المشاريع ومكتباتها واختباراتها وإصلاحاتها، وتصنيف المخاطر
الواقعية مع السبب والإصلاح والتوثيق.

> نطاق هذا التقرير: فحص كود المصدر، تدفقات HTTP، بنية قاعدة البيانات، واجهة
> المستخدم، محرك SMTP، ونشر. تمت مراجعة الطبقات التالية: API/HTTP، المصادقة،
> التخزين والأمان، الواجهة، المحرك، البنية التحتية، الاختبار.

---

## ١. ملخص تنفيذي

المشروع في مراحله الحالية لديه بنية برمجية متينة نسبياً، وأقوى جزء هو منظومة
الأمان (Argon2id + RLS + Vault + CSP + CSRF + Throttling + Audit). أعلى مخاطر
التعمق كانت: (1) صحة حارس `same-origin`، (2) تذبذب أرقام الوثائق، (3) تسريب
نصوص البنية التحتية في الواجهة.

---

## ٢. تحليل كل طبقة — نقاط القوة والمخاطر

### ٢.١ طبقة المعمارية (Architecture)
- **القوة:** طبقات موحدة للقراءة، أنواع أخطاء صريحة، ترحيلات مرقّمة.
- **المخاطر:** pool/DB failure handling غير مفصّل.

### ٢.٢ طبقة API / HTTP
1. **مخاطرة: حارس Cross-Origin (الأعلى أولوية).**
   - السبب: كان يطابق `Origin` بـ `Host` حرفياً؛ أي خلط بين `localhost` و`127.0.0.1`
     أو rewrite من proxy → رفض `403 cross-origin form submission rejected`.
   - التحقق: `Origin: http://localhost:8099` + `Host: 127.0.0.1:8099` → `403`.
   - الإصلاح: قاعدة loopback-equivalence مع اشتراط `Sec-Fetch-Site == same-origin`.
   - الحالة: مكتوب ومُفحص (`cargo check` سليم)؛ **معلق**: إعادة بناء + إعادة تشغيل
     + تشغيل اختبارات الوحدة الجديدة + clippy قبل الاعتماد.

### ٢.٣ طبقة المصادقة والجلسات
- **القوة:** Argon2id OWASP، SHA-256 للسر (256-bit)، deny-all credentials.
- **المخاطر:** limiter في الذاكرة (P2 عند التوسع).

### ٢.٤ طبقة التخزين والأمان
- **القوة:** RLS + GUC + composite FK + Vault + CHECK.
- **المخاطر:** KMS/per-tenant keys ناقصة (معلنة)؛ Vault stream truncation.

### ٢.٥ طبقة الواجهة
- **المخاطرة:** نصوص البنية التحتية في الواجهة (`PostgreSQL`, `RLS`, `audit_log`,
  `Stalwart`, `TIRA LABS — لا موارد خارجية — RLS مفعّل`). سبب: أماني/UX (فقدان
  الثقة)، الإصلاح: إزالة النصوص وإبقاءها في الوثائق فقط.

### ٢.٦ طبقة المحرك (SMTP/Stealwart/Rspamd)
- **القوة:** open-relay guard عبر RCPT-time refusal.
- **المخاطرة:** `MailHandler` default accepts all.

### ٢.٧ البنية التحتية
- **المخاطرة:** TLS native-tls (بدل rustls).
- **اكتشاف جديد عبر المهارة Browser:** 502 Bad Gateway عند فتح الموقع داخل تطبيق
  OpenCode على `127.0.0.1:8099`.

### ٢.٨ الاختبار والقياس
- Gates: fmt/check/clippy ✅، test 176/176 ✅.
- إضافة جديدة: اختبارات same-origin (8).

## ٤. كيف يعمل الإصلاح (وصف تقني مختصر)

- قبل: `Origin == Host` → reject عند mismatch.
- بعد: (أ) `Sec-Fetch-Site == cross-site` → reject؛ (ب) authority مطابقة → allow؛
  (ج) loopback (localhost/127.0.0.1/[::1]) مع `Sec-Fetch-Site == same-origin` (أو غياب) → allow.
- هذا يسمح بسياقات proxy/preview مع الحفاظ على أمن CSRF.

## ٥. ما تم توثيقه الآن في ملف واحد

- ملخص كل طبقة.
- المخاطر مع السبب والإصلاح.
- الإصلاح الحالي مع آلية العمل.
- اكتشاف جديد (502).
- حالة كل مخاطرة (مفتوح/مُصيّح/معلن).

---

## ٦. نطاق التحليل وما لم يُغطَّ بعد

- فحص جزئي معروف لـ `tira-provision` و`store delivery` و`frontend components` الكاملة.
- `cargo audit` و`cargo deny` غير منفذان رسمياً.
- اختبار أجهزة/Playwright غير منفذ.

---

## ٧. ملخص نهائي للتحليل المتعمق

1. **الأعلى:** حارس origin الصارم — أُصلح في الكود.
2. **المفتوح:** توحيد الوثائق، إزالة نصوص البنية التحتية، تفعيل cargo audit، تفعيل handler حقيقي، اعتماد rustls.
3. **المكتشف حديثاً:** فشل المتصفح الداخلي (502) — تشغيلي.

---

## ٨. توصيات متبقية قبل الاحترافية

1. إعادة البناء/إعادة التشغيل الخادم بعد تعديل الحارس.
2. تنفيذ التوحيد الوثائقي.
3. إزالة نصوص البنية التحتية من الواجهة.
4. اعتماد rustls.
5. تشغيل `cargo audit`.
6. تفعيل `MailHandler` production.
